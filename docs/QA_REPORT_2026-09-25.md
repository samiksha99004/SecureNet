## 2. Bugs found and fixed

| ID | Severity | Problem | Fix |
|---|---|---|---|
| R1 | Medium | **Live alerts silently stopped.** If the live connection dropped (server restart, laptop sleep, Wi-Fi blip) more than 60 minutes after sign-in, the dashboard reconnected with the expired access token. The server refused it forever, so pop-ups and the bell stopped working while the page looked normal. The server also rejected bad tokens before the handshake, so the browser could not tell "expired token" from "network down". | Frontend: every reconnect first gets a fresh token (`freshAccessToken()` in `apiClient.ts`). A token the server rejects is refreshed once before retrying. Reconnecting never gives up (every 30 s) and shows "Connection error" after 10 tries. Backend: the WebSocket accepts and then closes with code **1008**, so the browser knows the token was the problem. |
| R2 | Medium | **Turning the IDS on twice at once started two packet sniffers.** Two quick "ON" clicks, or two users at the same moment, both passed the "already running?" check while capture was starting. The second sniffer was never stopped. | `IDSService.start()` / `stop()` run one at a time behind a lock. A new test proves only one capture opens and that stop really stops it. The test fails on the old code. |
| R3 | Low | **Sign-in response time revealed which emails are registered** (unknown email 7 ms vs. known email 54 ms). Password checking also ran on the server's main loop. | An unknown email is now checked against a dummy password hash (38 ms vs. 27 ms after the fix). Password checks run in a worker thread. New test. |
| R4 | Low | `GET /api/events?page=100000000000000000000` crashed with a server error (500). | Page number capped at 1,000,000 → clean 422 message. New test. |
| Q5 | Low (open issue closed) | Old "generate / list / download / delete saved report" endpoints were still callable by any signed-in user and wrote files to the server's disk, although the dashboard no longer used them. | Removed. Only the daily reports remain. A test checks the old addresses are gone. |
| R5 | Environment | After the project folder was renamed from `SecureNet (3)` to `SecureNet`, the venv's `pip.exe`, `alembic.exe` and `uvicorn.exe` pointed to the old folder and failed. The launchers were not affected because they use `python -m …`. | Same package versions reinstalled from the F: cache, so the commands work again. |

## 3. What was checked and works

- **Sign-up with a code:** a wrong code counts down the attempts, a late (11 min) code is refused, a new code works, a weak or mismatched password is refused, and the setup token is single-use and not an access token. Admin is decided by `ADMIN_EMAILS`; everyone else is a SecureNet User.
- **Sign-in:** email is case-insensitive; a wrong password and an unknown email give the same message; lockout after 5 wrong passwords; refresh and access tokens can't be swapped; garbage tokens are refused.
- **Forgot password:** same answer for known and unknown emails; the reset token works once; the old password stops working.
- **Permissions:** anonymous users are blocked from all private routes; SecureNet Users are blocked from every admin change (settings, whitelist, model reload, resolving incidents); users can switch the IDS ON/OFF.
- **Input safety:** invalid sort columns, SQL-like search text, bad dates, severities, days, time zones, export formats and IDs, broken JSON and a 100 kB password all get clean 4xx answers. Every error has the `{status, code, message}` shape. API docs are hidden. CORS only allows the dashboard.
- **Live pipeline:** a fake-detector attack goes through the real IDS code. It is stored, pushed live (score and alert), and emailed after the batch window: the normal email to users, the `[SecureNet Admin]` email with user and event details to the admin, both with the `.txt` incident report. Attack names are HTML-escaped.
- **Reports:** a daily box appears with the right counts; `.txt`, `.csv` and `.pdf` downloads work; history CSV export works.
- **Support:** messages reach the contact email with Reply-To set to the user; a line break in the subject can't inject mail headers; limit of 1 message per minute.
- **Profile change:** needs the emailed code; one user's change token can't be used by another user.
- **Neon database:** migration `d5f9a3c7e2b8` applied; schema matches the code exactly; one row in each settings table; 2 active users (1 admin, 1 SecureNet User); 0 events, 0 unfinished sign-ups, 0 stale codes; IDS mode `MONITOR`; email alerts on for all severities.

## 4. Known test artefact

*"Resend available right after a code expired"*: the test script makes a code look 11 minutes old, but the page's own
60-second resend timer is still running, so the button is hidden. For real users a code expires after 10 minutes, long
after the 60-second timer. **Not an app bug.**
